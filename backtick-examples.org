* Why there is a pipe at all

~views::filter(r, pred)~ is the primary overload. ~views::filter(pred)~ is a
closure that remembers ~pred~ and waits for a range, and ~operator|~ is what
finally applies it. Two of those three exist because C++ has no way to write
the first one between its arguments.

It has one now.

#+begin_src c++
r | views::filter(pred) | views::transform(fn)      // today
r `views::filter` pred `views::transform` fn        // the same calls
#+end_src

The backtick binds tighter than every other binary operator and associates to
the left, so the chaining is free and no stage needs a parenthesis. Nothing
else changes: same overload resolution, same ADL, same laziness, same
codegen. It is a call.

Every example here is compiled twice, once in each spelling, by the same
compiler at the same settings, and a test requires the two binaries to print
the same bytes. Two programs agreeing isn't evidence on its own (they can be
wrong together), so each pair is also pinned to a checked-in golden. And
the ~|~ half is compiled with =-fno-backtick=, so it is code proven to build
with the feature off. Code that merely happens not to use it would prove
nothing.

* The calendar

The largest ranges pipeline anyone points at: Niebler's calendar, six stages
at the top level and three more nested inside them. Ported to ~std::ranges~
and ~std::chrono~, so ~boost::gregorian~, ~boost::format~ and the
hand-written ~interleave_view~ are gone. It prints 2015, three months to a
line, and the first twenty-seven lines are byte-identical to the output
documented in the original, which is a better check on the port than any
assertion I would have written.

* Senders

The same story, since ~then(sndr, fn)~ is also a primary overload:

#+transclude: [[file:src/examples/senders/chain.backtick.cpp::a2c278fa-1f76-4548-972a-885c7d276169]] :lines 2- :src c++ :end "a2c278fa-1f76-4548-972a-885c7d276169 end"

~when_all~ is variadic and stays a call. ~sync_wait~ takes nothing beyond the
sender and keeps the helper.

** Where it goes past replacing a pipe

~starts_on(sched, sndr)~ takes its scheduler first and has no one-argument
closure form. There is no ~sndr | starts_on(sched)~ to write, and there never
was: today the pipeline has to be broken open into a call and then resumed. An
infix operator does not care which argument is the subject.

#+transclude: [[file:src/examples/senders/hop.backtick.cpp::df720525-1992-407d-b375-908af9ec77ca]] :lines 2- :src c++ :end "df720525-1992-407d-b375-908af9ec77ca end"

Each stage reports the thread it actually ran on, so ~A B~ is evidence and not
a caption.

The range algorithms are the same shape and the same win. ~ranges::count~,
~ranges::contains~, ~ranges::equal~ all take the range first and have no
closure form, so ~r `ranges::count` x~ is reachable and ~r | count(x)~ never
was.

** Where it stops

P2300's asynchronous inclusive scan. ~bulk(sndr, policy, shape, f)~ takes four
arguments; a backtick operator is binary. There is no infix spelling
of a four-argument call, and this proposal doesn't invent one.

#+transclude: [[file:src/examples/senders/scan.backtick.cpp::b38693ad-2fc4-46f8-bda3-70efeee491bd]] :lines 2- :src c++ :end "b38693ad-2fc4-46f8-bda3-70efeee491bd end"

So ~bulk~ keeps its closure and ~pipe~ carries it. That is the honest shape of
the result: the pipe idiom survives where the arity doesn't fit, and nowhere
else.

* Do notation, desugared

Haskell had the pipe's problem first -- chained continuations read
inside-out -- and answered it with syntax. A ~do~ block is sugar over exactly
two binary operators, and the closing example of the wikibooks chapter that
teaches this ([[https://en.wikibooks.org/wiki/Haskell/do_notation][Haskell/do notation]]) is built so that every desugaring rule
fires at least once:

#+begin_src haskell
nameReturnAndCarryOn = do putStr "What is your first name? "
                          first <- getLine
                          putStr "And your last name? "
                          last <- getLine
                          let full = first++" "++last
                          putStrLn ("Pleased to meet you, "++full++"!")
                          return full
                          putStrLn "I am not finished yet!"
#+end_src

The Haskell 2010 report (§3.14) rewrites a ~do~ block one statement at a
time:

#+begin_src haskell
do {e}              =  e
do {e; stmts}       =  e >> do {stmts}
do {v <- e; stmts}  =  e >>= \v -> do {stmts}   -- v a plain variable, so the
                                                -- match cannot fail and no
                                                -- MonadFail case is needed
do {let ds; stmts}  =  let ds in do {stmts}
#+end_src

Working down the block, always rewriting the first statement. The ~;~ rule
peels off the prompt:

#+begin_src haskell
putStr "What is your first name? " >>
do first <- getLine
   ...
#+end_src

The ~<-~ rule turns the binding into a lambda, which swallows the rest of the
block -- this is where a later statement gets its right to mention ~first~:

#+begin_src haskell
putStr "What is your first name? " >>
(getLine >>= \first ->
 do putStr "And your last name? "
    ...)
#+end_src

The same two rules bind ~last~, and the ~let~ rule is next:

#+begin_src haskell
... (getLine >>= \last ->
     let full = first ++ " " ++ last
     in do putStrLn ("Pleased to meet you, " ++ full ++ "!")
           return full
           putStrLn "I am not finished yet!")
#+end_src

Two more uses of the ~;~ rule and the final ~do {e} = e~, and no sugar
remains:

#+begin_src haskell
nameReturnAndCarryOn =
  putStr "What is your first name? " >>
  (getLine >>= \first ->
   putStr "And your last name? " >>
   (getLine >>= \last ->
    let full = first ++ " " ++ last
    in putStrLn ("Pleased to meet you, " ++ full ++ "!") >>
       (return full >>
        putStrLn "I am not finished yet!")))
#+end_src

Note what ~return full~ became: one more statement, sequenced with ~>>~ like
any other. It neither ends the computation nor sets its result -- the block
has the type of its /last/ statement, and the extra line still prints.

Everything left standing is Monad. The continuations handed to ~>>=~ use the
values bound by earlier statements, which is exactly the dependency
Applicative cannot express, so the translation targets the Monad typeclass
from [[https://github.com/steve-downey/transpose][beman.transpose]] (P3200's typeclass-object pattern). The pieces map as

| Haskell          | C++                                                  |
|------------------+------------------------------------------------------|
| ~IO a~           | ~IO<A>~, a function from the world to an ~A~         |
| ~m >>= f~        | ~mbind(m, f)~, the typeclass basis                   |
| ~m >> k~         | ~then(m, k)~, defined as ~m >>= \_ -> k~, its default |
| ~return x~       | ~pure(x)~ -- C++ has plans for the word ~return~     |
| ~\v -> e~        | a by-value lambda                                    |
| ~let v = e in~   | a local variable in the continuation                 |

~IO~ is the teaching model of IO, with the world scripted down to the lines
the user has yet to type, so the pair is deterministic and the golden can pin
it:

#+transclude: [[file:src/examples/donotation/io_monad.hpp::5bcec8e5-8043-45e0-8175-a7b0166028f7]] :lines 2- :src c++ :end "5bcec8e5-8043-45e0-8175-a7b0166028f7 end"

The desugared term, translated call for call with the calls spelled prefix,
nests exactly as Haskell's did:

#+transclude: [[file:src/examples/donotation/carryon.pipe.cpp::d2b6e88f-3a9e-4601-8574-b4ef8561bcf8]] :lines 2- :src c++ :end "d2b6e88f-3a9e-4601-8574-b4ef8561bcf8 end"

And the sugar came off onto two /binary/ operators -- which is what an
operator is in Haskell, an infix name for a two-argument function -- so under
this proposal both go back between their arguments:

#+transclude: [[file:src/examples/donotation/carryon.backtick.cpp::3c0c7dba-b924-45ce-960f-bab25956a4fc]] :lines 2- :src c++ :end "3c0c7dba-b924-45ce-960f-bab25956a4fc end"

~pure~ takes one argument and stays a call, the same boundary the scorecard
draws. The parentheses around each right-hand side are the one piece of
Haskell that does not carry over: there the trailing lambda extends to the
end of the expression, while the backtick is left-associative and binds
tightest, so the grouping is spelled. And the syntax is no coincidence --
~m `mbind` f~ between its arguments /is/ Haskell's own backtick notation,
~x `div` y~, come home with the semantics attached.

* What converts, and what does not

The table below is printed by a program that compiles one instance of each
shape, so it cannot drift away from what the compiler accepts. Every claim in
it is a ~static_assert~ or it is not made.

#+transclude: [[file:src/examples/scorecard/scorecard.cpp::1d233eaa-37b0-43c9-815c-699b3772aba3]] :lines 2- :src c++ :end "1d233eaa-37b0-43c9-815c-699b3772aba3 end"

One row of it is a finding, not a feature. The design records D16 (a type name
in the slot constructs, with CTAD) as resolved, and the wording
example in the paper carries ~a `std::pair` b~. Neither prototype accepts it,
in any spelling. Clang refuses a slot that names a type at all; GCC accepts
the name and then looks for ~operator()~ on an object of that type. Neither
reaches functional-style construction, which is its own grammar production, so
D16 doesn't fall out of "a type name is callable" the way the design assumes.
That is DEV-06 and DEV-G12.

* What the examples turned up

Three things, none of which I'd have found from one-line examples.

D16 is not implemented, above.

A bare slot name in a dependent context is rejected by GCC and accepted by
Clang. ~t `pipe` inc~ inside a function template, where ~pipe~ is a variable
brought in by a using-declaration, fails at instantiation: GCC re-runs the
lookup at the point of instantiation and keeps only the ADL result, discarding
the ordinary lookup from the definition context. ADL finds nothing, since the
callee is a variable. Since the slot desugars to a call it should inherit the
call's lookup, so Clang has it right. A qualified slot works on both. That is
DEV-G11, and it bit twice in ordinary generic code.

And the pipe half of the calendar is harder to read than the backtick half, at
the same column limit, formatted by the same tool. I didn't set out to demonstrate that.
